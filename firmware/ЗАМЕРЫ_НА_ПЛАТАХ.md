# Прошивка LACERT — что проверить на платах

## Что уже проверено на моей стороне

Собрать настоящую прошивку я не могу — нет ESP-IDF и компиляторов под
Xtensa/RISC-V. Но проверено то, что от них не зависит:

- **Криптомодуль компилируется против mbedTLS 3.6.3** — той же версии, что
  входит в ESP-IDF v5.4. Собрал библиотеку из исходников и скомпилировал
  `main/lacert_crypto.c` вместе с ML-KEM (PQClean) и BLAKE3. Ошибок и
  предупреждений нет.
- **Обе ветки переключателя дают верные подписи** — по 50 подписей двумя
  разными ключами, каждая проверена независимым контекстом (так же, как это
  делает шлюз). Ноль расхождений.
- **Полный протокол работает** — отладочный клиент из `linux-debug/`
  (тот же `lacert_wire.c` и `lacert_client.c`, что поедут на плату) отработал
  против настоящего Go-шлюза: регистрация, рукопожатие, 10 пакетов телеметрии,
  2 ротации ключа, 4 ответа на проверку целостности прошивки, 0 ошибок.
  Метрики шлюза подтвердили: `handshakes_completed=1`, `rotations_succeeded=2`,
  `firmware_checks_passed=4`, отказов нет.

Чего это **не** доказывает: что код соберётся компилятором под Xtensa/RISC-V и
поведёт себя так же на железе. Это и предстоит проверить.

---

## Главное: переключатель оптимизации ECDSA

В `main/lacert_crypto.c` в начале файла:

```c
#define LACERT_SHARED_CRYPTO_CTX 1
```

- **1** — генератор случайных чисел и параметры кривой P-256 создаются один
  раз и переиспользуются (оптимизация);
- **0** — исходное поведение: контекст создаётся заново на каждую подпись.

Обе ветки в одной прошивке, переключаются одной цифрой. Это позволяет измерить
их на **одной плате и в одинаковых условиях** — иначе разница может оказаться
следствием разных сборок, а не самой оптимизации.

### Зачем это нужно

Замер на mbedTLS 2.28 показывал выигрыш в 2,6 раза. Но ESP-IDF v5.4 использует
**mbedTLS 3.6**, и на ней разницы нет: 348,2 мкс против 347,4 мкс по медиане
пятнадцати прогонов на x86-64.

На ESP32 источник энтропии другой — аппаратный генератор вместо подсистемы ОС.
Поэтому результат может отличаться, и проверить это можно только на плате.

---

## Порядок замеров

Для каждой платы (**XIAO ESP32-C6** и **XIAO ESP32-S3** — они различаются
наличием аппаратного ускорителя ECC, это самое интересное).

### 1. Подготовка

```bash
cd firmware
# заполнить в main/main.c: Wi-Fi, IP шлюза, LACERT_DEVICE_ID (уникальный!)
rm -rf build sdkconfig
idf.py set-target esp32c6        # или esp32s3
idf.py build
```

Проверить, что применилась оптимизированная конфигурация:

```bash
grep -E 'COMPILER_OPTIMIZATION|MBEDTLS_HARDWARE' sdkconfig
```

Если увидишь `-Og` вместо `-Os` — замеры будут бессмысленными: отладочная
сборка на порядок медленнее.

### 2. Замер с оптимизацией (значение 1, как в архиве)

```bash
idf.py -p /dev/ttyACM0 flash monitor
```

Из вывода блока «МИКРОБЕНЧМАРК КРИПТОГРАФИИ» записать **всю таблицу**.
Достаточно одного прогона: операции миллисекундные, шум на них влияет слабо.

### 3. Замер без оптимизации

Поменять в `main/lacert_crypto.c` значение на `0`, затем:

```bash
idf.py build
idf.py -p /dev/ttyACM0 flash monitor
```

Пересобирать с нуля не нужно — меняется один файл.

## Важные напоминания

**Уникальный `LACERT_DEVICE_ID` каждой плате.** Шлюз хранит один набор ключей
на идентификатор; вторая плата с тем же именем не пройдёт рукопожатие.

**Перепрошивка меняет SHA-256 образа.** Шлюз держит эталонный хеш с момента
регистрации, поэтому после перезаливки проверка целостности провалится и
устройство будет отозвано — это правильное поведение, но при частых
перепрошивках мешает. Перед каждой перезаливкой:

```bash
psql "$LACERT_PG_DSN" -c "DELETE FROM devices WHERE device_id='xiao-c6';"
```

Либо, если шлюз работает без базы, просто перезапустить его.

**Порты:** XIAO — `/dev/ttyACM0`, ESP32-S3-DevKitC-1 — `/dev/ttyUSB0`.

**При смене цели** (`esp32c6` ↔ `esp32s3`) обязательно `rm -rf build sdkconfig`,
иначе сборка подхватит настройки от предыдущей платы.

## Заодно исправлено в документации

**Команда сборки `bench_host` не работала.** В `MEASUREMENTS.md`, раздел 6.2,
не хватало флага `-I.`, и сборка падала на отсутствующем `esp_random.h`:

```
../main/lacert_crypto.c:18:10: fatal error: esp_random.h: No such file or directory
```

Добавил заглушку `linux-debug/esp_random.h` (берёт случайность из
`getrandom(2)`, при недоступности — из `/dev/urandom`, и аварийно завершается,
если источника нет) и поправил команду в обеих языковых версиях. Теперь замеры
на базовой платформе воспроизводятся по документации.
