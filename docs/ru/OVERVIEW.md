# LACERT — обзор проекта

Единая точка входа в документацию. Здесь — что это, из чего состоит, как
собрать и запустить каждую часть, и куда смотреть за деталями.

LACERT (Lightweight Autonomous Continuous Encryption with Refreshment Tokens) —
полностью локальная (без облака) система защищённого подключения IoT-устройств
к корпоративной сети с постквантовой криптографией. Состоит из двух частей:

- **шлюз** — сетевая служба на Go (`cmd/gatewayd`);
- **прошивка** — клиент протокола на C для ESP32 (`firmware/`).

Обе части реализуют один и тот же протокол и проверены во взаимной работе на
реальном железе: XIAO ESP32-C6 (RISC-V), XIAO ESP32-S3 и ESP32-S3-DevKitC-1
(Xtensa).

## Что делает система

1. **Регистрация.** Устройство генерирует пару ключей (ECDSA P-256 для подписи
   и ML-KEM-1024 для обмена ключами), считает контрольную сумму и регистрируется
   на шлюзе через REST. Ключи хранятся на устройстве (NVS/efuse) и переживают
   перезагрузку.
2. **Рукопожатие.** Постквантовое: обмен ключами по ML-KEM-1024, вывод сессионного
   ключа через BLAKE3, аутентификация подписью ECDSA. По сравнению с TLS не
   требует инфраструктуры открытых ключей — идентичность привязана к устройству.
3. **Передача данных.** Телеметрия шифруется ChaCha20-Poly1305.
4. **Непрерывная ротация ключей.** Каждые ~5 минут (настраивается) сессионный
   ключ обновляется с подмешиванием свежего секрета ML-KEM — это даёт прямую
   секретность (PFS) и постквантовую безопасность после компрометации (PCS).
5. **Проверка целостности прошивки.** Периодически шлюз шлёт challenge; устройство
   подписывает `challenge || SHA-256(образ прошивки)` — так шлюз убеждается, что
   на устройстве работает та прошивка, что была зарегистрирована.

Подробности каждого шага, форматы кадров и полей — в `PROTOCOL_SPEC.md`.

## Ключевой результат исследования

Гипотеза о выгоде постквантовой подписи SLH-DSA не подтвердилась: её подпись
примерно в 11 000 раз медленнее ECDSA (сотни миллисекунд) и в ~110 раз объёмнее
(7856 байт против 71). Вывод: **постквантовую стойкость держим на уровне обмена
ключами (ML-KEM-1024), подпись оставляем на ECDSA P-256.** Система поддерживает
оба алгоритма подписи (переключение через `SigAlgorithm`), но по умолчанию и на
устройстве используется ECDSA.

**Замеры на реальных платах этот вывод подкрепляют.** Даже ECDSA на
микроконтроллере стоит дорого: 22 мс на ESP32-C6 и 170 мс на ESP32-S3 (на
сервере — 0,35 мс). SLH-DSA, будучи на порядки тяжелее, на таких кристаллах
просто нежизнеспособна. При этом сам ML-KEM обходится умеренно — 16–23 мс, и
почти не зависит от платформы.

Сравнение с DTLS 1.2 при сопоставимых гарантиях: LACERT устанавливает сессию
в 3,2 раза быстрее, а постквантовый обмен ключами ML-KEM обходится дешевле
классического ECDHE в 11 раз на сервере и в 13–15 раз на платах ESP32. Подробно
— в `MEASUREMENTS.md`, раздел 3.5.

Отдельный результат: **ECDSA на ESP32-C6 быстрее, чем на ESP32-S3, в 7,7 раза**
— несмотря на то, что C6 слабее (160 МГц против 240, одно ядро против двух). На
остальных операциях платы идут вровень, так что дело именно в аппаратном
ускорителе эллиптических кривых, который есть у C6 и отсутствует у S3. Для
криптографии на микроконтроллере профильный ускоритель важнее тактовой частоты.
Полная таблица — в `FIRMWARE.md`.

## Сборка и запуск шлюза

Требования: Go 1.22+. Для боевого хранилища — PostgreSQL (без него шлюз работает
на памяти).

```bash
# сборка
go build -o gatewayd ./cmd/gatewayd

# запуск (память, без БД) — удобно для проверки
LACERT_HTTP_ADDR=:8080 LACERT_TCP_ADDR=:7700 ./gatewayd

# открыть дашборд
xdg-open http://localhost:8080
```

Боевое развёртывание одной командой (systemd, /opt/lacert, PostgreSQL):

```bash
sudo bash deploy/bare-metal/install.sh
```

Скрипт идемпотентен и не перезаписывает существующий
`/etc/lacert/gatewayd.env`. Подробности — в `GATEWAY.md`.

## Сборка и заливка прошивки

Требования: ESP-IDF v5.4.x (**релизный тег**, не промежуточный коммит ветки —
на сырых коммитах сборка ESP-IDF может падать). Поддержаны XIAO ESP32-C6
(RISC-V), XIAO ESP32-S3 и ESP32-S3-DevKitC-1 (Xtensa). **Все три платы
проверены на реальном железе** — проходят полный протокол против шлюза.

```bash
cd firmware
# заполнить настройки в main/main.c (WiFi, IP шлюза, device_id, токен)
idf.py set-target esp32s3      # или esp32c6
idf.py build
idf.py -p /dev/ttyUSB0 flash monitor
```

Полная инструкция, настройка стенда и разбор частых проблем — в
`FIRMWARE_BUILD.md`. Устройство прошивки изнутри — в `FIRMWARE.md`.

## Отладка без железа

Тот же клиентский код (`firmware/main/lacert_wire.c` и `lacert_client.c`)
собирается под Linux в `firmware/linux-debug/` — с криптографией на OpenSSL.
Позволяет прогнать весь протокол против шлюза без платы. См.
`LINUX_DEBUG.md`.

## Проверки и тесты

```bash
go build ./...        # сборка всего
go vet ./...          # статический анализ
go test ./...         # модульные тесты (14 пакетов)
go test -race ./...   # проверка гонок
```

Комплексный стресс-тест пяти защитных механизмов (подделка подписи, replay,
устаревший challenge, чужой ключ, повреждение кадра) — в
`internal/gateway/stress_test.go` и `cmd/stresstest/`.
