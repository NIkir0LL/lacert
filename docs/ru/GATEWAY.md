# Шлюз LACERT — архитектура и API

Шлюз (`cmd/gatewayd`) — самостоятельная сетевая служба на Go. Принимает
подключения устройств по TCP, ведёт с ними протокол LACERT, хранит устройства и
телеметрию, отдаёт REST API и веб-дашборд, публикует данные в MQTT.

## Слои

```
                    ┌─────────────────────────────────────┐
   устройства ─TCP─►│ transport/tcpserver → gateway        │
   (ESP32)   :7700  │   рукопожатие, данные, ротация,       │
                    │   проверка прошивки                   │
                    ├─────────────────────────────────────┤
   браузер ──HTTP──►│ api (REST) + webui (дашборд)  :8080  │
   админ/скрипты    ├─────────────────────────────────────┤
   подписчики ─────►│ mqttbridge (брокер)          :1883  │
                    ├─────────────────────────────────────┤
                    │ scheduler — фоновые ротации/проверки  │
                    ├─────────────────────────────────────┤
                    │ store — memstore | pgstore (Postgres) │
                    └─────────────────────────────────────┘
```

Пакеты:

- **`internal/gateway`** — ядро: состояние сессий, инициирование ротации,
  выдача и проверка firmware-challenge, обработка ACK, отзыв устройств.
- **`internal/transport/tcpserver`** — приём TCP-подключений, чтение/запись
  кадров, передача в gateway.
- **`internal/wire`** — бинарное кадрирование (см. `PROTOCOL_SPEC.md`).
- **`internal/crypto`** — ML-KEM-1024, ECDSA P-256, BLAKE3, ChaCha20-Poly1305,
  вывод и ротация ключей.
- **`internal/api`** — REST на `chi`, аутентификация по Bearer-токену.
- **`internal/webui`** — дашборд (HTML/CSS/JS, вшит в бинарник через go:embed).
- **`internal/store`** — интерфейс хранилища; `memstore` (память) и
  `pgstore` (PostgreSQL через gorm, таблицы `devices`, `telemetry_readings`,
  `key_rotations`, `session_events`).
- **`internal/scheduler`** — по таймеру обходит активные сессии и запускает
  ротацию ключей и проверку прошивки.
- **`internal/mqttbridge`** — встроенный MQTT-брокер (`mochi-mqtt`);
  расшифрованная телеметрия идёт в `devices/{id}/telemetry`, события — в
  `devices/{id}/events`.
- **`internal/telemetry`** — разбор полезной нагрузки и запись показаний.

## Порты (по умолчанию)

| Порт | Назначение | Переменная |
|------|-----------|------------|
| `:7700` | TCP-протокол устройств | `LACERT_TCP_ADDR` |
| `:8080` | REST API + дашборд | `LACERT_HTTP_ADDR` |
| `:1883` | MQTT-брокер | `LACERT_MQTT_ADDR` |

Чтобы устройства из локальной сети могли подключиться, адреса должны слушать
все интерфейсы (`:7700`, а не `127.0.0.1:7700`).

## REST API

База — `/api/v1`. Формат — JSON.

### Публичные (без токена)

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/healthz` | проверка живости, отдаёт `ok` |
| GET | `/api/v1/gateway` | публичный ML-KEM-ключ шлюза (нужен устройству для рукопожатия) |
| GET | `/api/v1/metrics` | счётчики работы шлюза (см. ниже) |

### Счётчики `/api/v1/metrics`

Метрики живут в памяти процесса и обнуляются при перезапуске шлюза. Показываются
на вкладке «Метрики» дашборда.

| Поле | Что считает |
|------|-------------|
| `handshakes_completed` | успешно завершённые рукопожатия |
| `handshakes_rejected` | отклонённые рукопожатия (неверная подпись, неизвестное или отозванное устройство) |
| `replays_blocked` | заблокированные повторы (replay): кадр с уже использованным nonce |
| `rotations_succeeded` | ротации ключа, подтверждённые устройством (ACK получен) |
| `rotations_failed` | ротации, откаченные по тайм-ауту ACK |
| `firmware_checks_passed` | пройденные проверки целостности прошивки |
| `firmware_checks_failed` | проваленные проверки (подпись не сошлась или хеш прошивки не совпал) |
| `firmware_checks_rejected` | ответы, отклонённые как устаревшие (позже `LACERT_FIRMWARE_VALIDITY`) |
| `devices_revoked` | отозванные устройства |
| `data_replays_blocked` | пакеты данных, отвергнутые как повтор (nonce уже принимался под текущим ключом) |
| `telemetry_dropped` | принятые показания, которые не удалось записать в хранилище |

Счётчик `telemetry_dropped` заслуживает отдельного внимания: он растёт, когда
пакет успешно принят и расшифрован, но запись в хранилище не удалась (например,
база недоступна). Обработка пакета при этом не прерывается — обрывать сессию
из-за проблем хранилища значило бы превращать сбой базы в отказ связи. Но
показания в этом случае теряются безвозвратно, поэтому ненулевое значение
требует разбирательства с базой, а не просто наблюдения.

Разница между `failed` и `rejected` для проверок прошивки существенна: **failed**
— устройство ответило, но ответ не сошёлся (признак подмены прошивки, ведёт к
отзыву); **rejected** — ответ пришёл слишком поздно (обычно медленная сеть, к
отзыву не ведёт).

### Защищённые (Bearer-токен)

Если задан `LACERT_ADMIN_TOKEN`, эти маршруты требуют заголовок
`Authorization: Bearer <token>`. Если токен не задан — аутентификация выключена
(удобно для локальной разработки, **не для прода**).

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/api/v1/devices` | список устройств и их статус |
| POST | `/api/v1/devices` | регистрация устройства |
| GET | `/api/v1/devices/{id}` | карточка устройства |
| GET | `/api/v1/devices/{id}/events` | журнал событий устройства |
| POST | `/api/v1/devices/{id}/revoke` | отзыв устройства |
| GET | `/api/v1/telemetry` | показания телеметрии |
| GET | `/api/v1/rotations` | журнал ротаций ключей |
| GET | `/api/v1/firmware-checks` | журнал проверок целостности прошивки (`?device_id=`, `?limit=`) |

### Регистрация устройства (тело POST /devices)

```json
{
  "device_id": "xiao-esp32-1",
  "identity_pub_hex": "04....",        // ECDSA P-256, 65 байт
  "kem_pub_hex": "....",               // ML-KEM-1024 pub, 1568 байт
  "firmware_hash_hex": "....",         // SHA-256 образа прошивки, 32 байта
  "checksum": "....",                  // hex(BLAKE3(id||idPub||kemPub||fwHash))[:8]
  "sig_algorithm": "ecdsa-p256"
}
```

Повторная регистрация того же `device_id` с теми же ключами возвращает 400/409
и это **штатно** (устройство просто уже известно). А вот регистрация того же
`device_id` с **другими** ключами будет отклонена, и рукопожатие такого
устройства не пройдёт — это защита от подмены. Поэтому у каждой физической
платы должен быть уникальный `device_id`.

## Конфигурация

Всё задаётся переменными окружения. **Полный справочник всех 25 переменных с
значениями по умолчанию — в [`CONFIG.md`](CONFIG.md)**; обоснование таймингов и
рекомендации по подбору — в [`TUNING.md`](TUNING.md).
Ключевые:

| Переменная | Назначение |
|-----------|-----------|
| `LACERT_HTTP_ADDR`, `LACERT_TCP_ADDR`, `LACERT_MQTT_ADDR` | адреса портов |
| `LACERT_ADMIN_TOKEN` | токен для защищённых REST-маршрутов |
| `LACERT_PG_DSN` | строка подключения к PostgreSQL (без неё — память) |
| `LACERT_ROTATION_INTERVAL` | период ротации ключей (по умолчанию 300 с) |
| `LACERT_FIRMWARE_INTERVAL` | период проверки прошивки (по умолчанию 1 ч) |
| `LACERT_CORS_ORIGINS` | разрешённые источники для дашборда |

Диагностические переменные (`LACERT_LOG_SESSION_KEYS`, `LACERT_EMULATE_DEVICES`
и пр.) предназначены для отладки и **должны быть выключены в бою**.

## Переменные вспомогательных утилит

Эти переменные относятся не к шлюзу, а к утилитам из `cmd/` — они пригодятся
при тестировании без реальных плат:

| Переменная | Утилита | Назначение |
|-----------|---------|-----------|
| `LACERT_GATEWAY_HTTP` | `devicesim`, `stresstest` | адрес REST шлюза (по умолчанию `http://localhost:8080`) |
| `LACERT_GATEWAY_TCP` | `devicesim`, `stresstest` | адрес TCP шлюза (по умолчанию `localhost:7700`) |
| `LACERT_DEVICE_ID` | `devicesim` | идентификатор симулируемого устройства |
| `LACERT_PROFILE` | `devicesim` | профиль датчиков (какие поля телеметрии слать) |
| `LACERT_STRESS_WAIT` | `stresstest` | пауза перед началом сценариев |
| `LACERT_STRESS_D4_DELAY` | `stresstest` | задержка ответа в сценарии D4 (проверка отклонения устаревшего challenge) |
| `LACERT_TEST_PG_DSN` | тесты `pgstore` | подключение к тестовой БД; без неё тесты PostgreSQL пропускаются |

## Устойчивость и ограничения ресурсов

**Тайм-ауты HTTP.** У сервера выставлены `ReadHeaderTimeout` (10 с),
`ReadTimeout` (30 с), `WriteTimeout` (60 с), `IdleTimeout` (120 с) и лимит на
размер заголовков (1 МБ). Без них медленный или враждебный клиент мог бы держать
соединения открытыми неограниченно долго и исчерпать ресурсы (slowloris) —
`http.Server` по умолчанию не выставляет никаких тайм-аутов.

**Тайм-ауты TCP.** На соединениях устройств стоят дедлайны чтения; незавершённые
рукопожатия протухают через `LACERT_PENDING_HANDSHAKE_TIMEOUT`.

**Ограничение памяти без БД.** Когда `LACERT_PG_DSN` не задан, шлюз хранит всё в
памяти. Журналы там ограничены (100 тыс. записей телеметрии, по 50 тыс. событий и
ротаций) с вытеснением самых старых: без этого при 10 устройствах с интервалом
2 с процесс набирал бы около 80 МБ в сутки и за неделю падал бы по нехватке
памяти. Для реального хранения истории используйте PostgreSQL.

**Индексы.** Основные запросы дашборда («последние N записей устройства»)
опираются на составные индексы `(device_id, created_at DESC)` по телеметрии,
ротациям и событиям, плюс отдельный индекс по `event_type` для вкладки проверок
прошивки. С раздельными индексами PostgreSQL был вынужден отбирать все записи
устройства и сортировать их; с составными — читает сразу нужные строки в нужном
порядке (на 300 тыс. записей это 0,25 мс вместо 1,0 мс, и разрыв растёт вместе с
историей). Индексы создаются автоматически при миграции.

**Восстановление после сбоев.** Паника в обработчике одного соединения
перехватывается и не роняет шлюз. Остановка по `SIGTERM`/`SIGINT` — плавная:
сервер дожидается активных запросов и закрывает сессии.

## Поведение под нагрузкой (замеры)

Нагрузочный тест на реальном PostgreSQL, **одно ядро CPU**, эмулированные
устройства с интервалом телеметрии 2 с, ротацией каждые 30 с и проверкой
прошивки каждую минуту (нагрузка заметно жёстче боевых значений по умолчанию —
300 с и 1 ч):

| Устройств | CPU | Память | Задержка `/devices` | Сбоев |
|-----------|-----|--------|---------------------|-------|
| 10 | 0,4 % | 20 МБ | 3 мс | 0 |
| 100 | 3,3 % | 34 МБ | 13 мс | 0 |
| 250 | 7,7 % | 57 МБ | 12 мс | 0 |
| 500 | 12,4 % | 93 МБ | 26 мс | 0 |

Все устройства выходят онлайн, ротации и проверки целостности проходят без
единого сбоя. Расход ресурсов растёт линейно: примерно **0,025 % CPU и 0,15 МБ
памяти на устройство**.

Криптография узким местом не является: на сервере рукопожатие занимает доли
миллисекунды, а ротация — десятки микросекунд (тяжело это только на самом
микроконтроллере, см. `FIRMWARE.md`). Ограничивают систему база данных и
сеть, а не вычисления.

Что было исправлено по итогам этих замеров:

- **Список устройств делал N+1 запросов.** `/api/v1/devices` запрашивал
  последнюю телеметрию отдельно для каждого устройства: при 500 устройствах это
  500 SQL-запросов на одно открытие дашборда. Теперь одна выборка
  (`DISTINCT ON`) на всех — задержка упала со 180 мс до 26 мс.
- **Пул соединений с БД не был ограничен.** При тысяче одновременно
  подключающихся устройств шлюз открывал соединения, пока PostgreSQL не начинал
  отвечать «too many clients» (у него лимит 100), и часть устройств не могла
  пройти рукопожатие. Теперь пул ограничен, и запросы ждут свободного соединения
  вместо отказа.

## Развёртывание

```bash
sudo bash deploy/bare-metal/install.sh
```

Ставит бинарники в `/opt/lacert/bin/` (`gatewayd`, `devicesim`), конфиг в
`/etc/lacert/gatewayd.env`, заводит
systemd-службу `lacert-gatewayd`. Скрипт идемпотентен и не перезаписывает
существующий `.env`. Управление:

```bash
systemctl status lacert-gatewayd
sudo systemctl restart lacert-gatewayd
journalctl -u lacert-gatewayd -f
```

## Работа с устройствами (PostgreSQL)

Список:
```bash
psql "$LACERT_PG_DSN" -c "SELECT device_id, status FROM devices;"
```

Удалить устройство (например, если стёрли NVS и надо переиспользовать id):
```bash
psql "$LACERT_PG_DSN" -c "DELETE FROM devices WHERE device_id='xiao-esp32-1';"
```

## Боевая сборка

Для продакшена стоит собрать шлюз без диагностических частей: исключить
`cmd/demo`, `cmd/stresstest`, `cmd/devicesim`, `internal/emulator`, выключить
`LACERT_EMULATE_DEVICES` и `LACERT_LOG_SESSION_KEYS`, задать `LACERT_ADMIN_TOKEN`
и настроить `LACERT_CORS_ORIGINS` под свой домен.
