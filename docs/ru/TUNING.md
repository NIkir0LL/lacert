# Настраиваемые параметры (для тестового стенда)

> Здесь — **обоснование** значений и рекомендации по подбору.
> Полный список всех переменных `.env` с дефолтами — в [`CONFIG.md`](CONFIG.md).

Все временные параметры системы можно переопределить через переменные
окружения шлюза (`cmd/gatewayd`) — без изменения кода и пересборки. Это удобно
для подгонки значений на стенде перед переходом к боевой системе с ESP32.

**Важно:** если переменная не задана, используется значение по умолчанию
(боевое). Так что для продакшена достаточно ничего не задавать.

## Таблица параметров

| Переменная окружения | По умолчанию | Что настраивает |
|---|---|---|
| `LACERT_ROTATION_INTERVAL` | `300s` | Как часто ротировать ключ по времени |
| `LACERT_ROTATION_PACKET_LIMIT` | `300` | Ротация после N переданных пакетов |
| `LACERT_ROTATION_ACK_TIMEOUT` | `5s` | Сколько ждать подтверждения (ACK) ротации, прежде чем считать её неуспешной |
| `LACERT_ROTATION_CHECK_PERIOD` | `5s` | Как часто планировщик опрашивает устройства |
| `LACERT_MAX_ROTATION_FAILURES` | `3` | Сколько неуспешных ротаций подряд до отзыва устройства |
| `LACERT_FIRMWARE_INTERVAL` | `1h` | Как часто проверять целостность прошивки |
| `LACERT_FIRMWARE_VALIDITY` | `15s` | Окно валидности ответа на challenge (позже — отклонён как устаревший) |
| `LACERT_FIRMWARE_CHALLENGE_TIMEOUT` | `25s` | Пауза перед повторной выдачей challenge тому же устройству |
| `LACERT_PENDING_HANDSHAKE_TIMEOUT` | `20s` | Протухание незавершённого рукопожатия |
| `LACERT_NONCE_TTL` | `5m` | Как долго помнить nonce для replay-защиты |

## Откуда взялись такие значения по умолчанию

Дефолты подогнаны под связку «ECDSA + локальная сеть» — ту, что реально
используется на платах (см. вывод анализа: подпись ECDSA, а не SLH-DSA).
Тайм-ауты выбраны с запасом относительно стоимости операций на самом
устройстве: подпись ECDSA занимает 22 мс на ESP32-C6 и 170 мс на ESP32-S3, то
есть доли секунды даже в худшем случае.

- **`LACERT_ROTATION_ACK_TIMEOUT` = 5s.** Хватает с запасом: ротация на ESP32
  укладывается в единицы миллисекунд вместе с сетью.
- **`LACERT_FIRMWARE_VALIDITY` = 15s.** Окно, за которое устройство обязано
  ответить на challenge. Короткое окно = меньше пространства для повторной
  отправки старого ответа.
- **`LACERT_PENDING_HANDSHAKE_TIMEOUT` = 20s.** Незавершённые рукопожатия не
  висят в памяти шлюза.
- **`LACERT_ROTATION_INTERVAL` = 300s.** Можно сокращать до 60–120s: чаще
  ротация = меньше данных под одним ключом. Ограничение — накладные расходы на
  самом устройстве. По замерам на железе одна ротация (декапсуляция ML-KEM +
  вывод ключа BLAKE3) стоит **18–23 мс** — ESP32-C6 около 18 мс, ESP32-S3 около
  23 мс. При интервале в минуту это доли процента процессорного времени.

  (В более ранних редакциях здесь стояла цифра ≈61 мкс — это была ротация на
  сервере x86-64. На микроконтроллере она на три порядка дороже, и планировать
  интервал нужно от цифр с железа. См. таблицу в `FIRMWARE.md`.)

Если вы переключитесь на **SLH-DSA**, эти окна нужно увеличить: на сервере её
подпись занимает ≈336 мс против ≈0,35 мс у ECDSA, а на микроконтроллере
разрыв будет ещё больше — уже ECDSA стоит там 22 мс (C6) и 170 мс (S3).
Ориентиры: `ROTATION_ACK_TIMEOUT` до 30s, `FIRMWARE_VALIDITY` до 90s,
`PENDING_HANDSHAKE_TIMEOUT` до 60s.

`RotationPacketLimit`, `MaxRotationFailures`, `NonceTTL` обычно можно оставить
как есть.

## Пример: тестовый стенд с короткими интервалами

```bash
LACERT_ROTATION_INTERVAL=60s \
LACERT_ROTATION_ACK_TIMEOUT=8s \
LACERT_FIRMWARE_INTERVAL=30m \
LACERT_FIRMWARE_VALIDITY=15s \
LACERT_PENDING_HANDSHAKE_TIMEOUT=20s \
./gatewayd
```

## Пример: демо-режим для живого стресс-теста (очень короткие интервалы)

Используется в `deploy/run-live-stress.sh`, чтобы все сценарии отработали за
~20 секунд. НЕ для продакшена:

```bash
LACERT_ROTATION_INTERVAL=6s \
LACERT_ROTATION_ACK_TIMEOUT=4s \
LACERT_FIRMWARE_INTERVAL=2s \
LACERT_FIRMWARE_VALIDITY=1s \
./gatewayd
```

## Как найти оптимум на стенде

1. Запусти шлюз с эмуляцией (`LACERT_EMULATE_DEVICES=3`) и разными значениями.
2. Смотри вкладку «метрики» на дашборде: если растут `rotations_failed` или
   `firmware_checks_rejected` при исправных устройствах — тайм-аут слишком
   мал, увеличь.
3. Когда перейдёшь на реальные ESP32 — начни с «безопасных» значений (ближе к
   умолчанию) и постепенно сокращай, наблюдая, что провалов не появляется.

## Живой стресс-тест: задержка D4

Сценарий D4 (устаревший firmware-challenge) отвечает на challenge намеренно
поздно, чтобы шлюз отклонил ответ. Задержка должна ПРЕВЫШАТЬ
LACERT_FIRMWARE_VALIDITY шлюза. По умолчанию задержка 20с (с запасом над окном
15с). Если вы увеличили окно валидности — увеличьте и задержку:

  LACERT_STRESS_D4_DELAY=35s go run ./cmd/stresstest   # если validity=30s
