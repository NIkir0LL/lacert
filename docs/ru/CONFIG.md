# Конфигурация шлюза — полный справочник `.env`

Шлюз настраивается только переменными окружения. В боевом развёртывании они
лежат в **`/etc/lacert/gatewayd.env`** и подхватываются systemd-службой
(`lacert-gatewayd`).

> **Важно.** Если запускать бинарник вручную (`./gatewayd`), переменные из
> `/etc/lacert/gatewayd.env` **не подхватятся** — шлюз стартует с настройками по
> умолчанию, то есть без базы (in-memory) и без авторизации. Для ручного запуска:
> ```bash
> sudo bash -c 'set -a; source /etc/lacert/gatewayd.env; set +a; /opt/lacert/bin/gatewayd'
> ```

Обоснование значений таймингов и рекомендации по их подбору — в
[`TUNING.md`](TUNING.md). Здесь — полный список.

---

## Сеть

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_TCP_ADDR` | `:7700` | адрес TCP-протокола устройств |
| `LACERT_HTTP_ADDR` | `:8080` | адрес REST API и дашборда |
| `LACERT_MQTT_ADDR` | `:1883` | адрес встроенного MQTT-брокера |
| `LACERT_CORS_ORIGINS` | не задан | разрешённые внешние источники для браузерных запросов (например `https://lacert.example.com`). Если не задан, кросс-доменные запросы не разрешаются: встроенный дашборд работает с того же адреса и в них не нуждается. Значение `*` открывает API любому сайту — задавайте осознанно |

Чтобы платы из локальной сети могли подключиться, адрес должен слушать все
интерфейсы (`:7700`), а не `127.0.0.1:7700`.

## Хранилище

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_PG_DSN` | не задан | строка подключения к PostgreSQL |

**Если `LACERT_PG_DSN` не задан, шлюз работает в памяти** и при перезапуске
теряет все устройства и телеметрию. В логе при старте будет предупреждение. Для
боевой работы задавать обязательно:

```
LACERT_PG_DSN=host=localhost user=lacert password=... dbname=lacert port=5432 sslmode=disable
```

## Безопасность

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_ADMIN_TOKEN` | не задан | токен для защищённых REST-маршрутов (`Authorization: Bearer <token>`) |
| `LACERT_NONCE_TTL` | `5m` | срок жизни nonce в защите от повторов (replay) |
| `LACERT_MAX_CONNECTIONS` | `1024` | предел одновременных соединений устройств. Сверх него подключения отклоняются сразу: каждое занимает горутину и буферы ещё до проверки регистрации |

Если токен не задан, **авторизация REST отключена** — годится только для
локальной разработки. Этот же токен вписывается в прошивку платы
(`LACERT_ADMIN_TOKEN` в `main.c`), она предъявляет его при регистрации.

## Ротация ключей

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_ROTATION_INTERVAL` | `300s` | как часто ротировать ключ сессии |
| `LACERT_ROTATION_PACKET_LIMIT` | `300` | ротация также по числу пакетов под одним ключом |
| `LACERT_ROTATION_ACK_TIMEOUT` | `5s` | сколько ждать подтверждения (ACK) ротации от устройства |
| `LACERT_ROTATION_CHECK_PERIOD` | `5s` | как часто планировщик обходит сессии |
| `LACERT_MAX_ROTATION_FAILURES` | `3` | сколько неудачных ротаций подряд до отзыва устройства |

### Как считается время до повторной попытки

Планировщик работает тактами по `ROTATION_CHECK_PERIOD`. На каждом такте он
сначала проверяет, не «зависла» ли отправленная ротация дольше
`ROTATION_ACK_TIMEOUT`, и только потом решает, не пора ли начать новую.

Поэтому если устройство **не ответило**:

```
t = 0                      шлюз отправил ротацию, ждёт ACK
t < ACK_TIMEOUT            такты проходят, ротация ещё не считается провальной
первый такт после
ACK_TIMEOUT                откат зависшей ротации, засчитана неудача №1
следующий такт             новая попытка ротации
```

**Время до повторной попытки ≈ `ACK_TIMEOUT` + до 2 × `CHECK_PERIOD`.**

Пример (частая конфигурация для демонстрации: `ACK_TIMEOUT=5s`,
`CHECK_PERIOD=2s`): откат на ~6-й секунде, повтор на ~8-й. То есть новая попытка
примерно **каждые 8–10 секунд**.

После `MAX_ROTATION_FAILURES` неудач подряд (по умолчанию 3, то есть ~25–30 с в
этом примере) шлюз **отзывает устройство**: продолжать обмен, когда ключ не
удаётся сменить, небезопасно. Счётчик неудач **сбрасывается при первой же
успешной ротации**, поэтому одиночные сбои связи не копятся до отзыва.

Для справки: сама ротация на плате (декапсуляция ML-KEM + вывод ключа BLAKE3)
занимает 18–26 мс, так что таймаут в 5 с — запас в двести раз. Если ротации
срываются, причина в потере связи, а не в нехватке производительности.

## Проверка целостности прошивки

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_FIRMWARE_INTERVAL` | `1h` | как часто проверять прошивку устройства |
| `LACERT_FIRMWARE_VALIDITY` | `15s` | окно, в течение которого ответ на challenge считается свежим |
| `LACERT_FIRMWARE_CHALLENGE_TIMEOUT` | `25s` | пауза перед повторной выдачей challenge тому же устройству |

Провал проверки (подпись не сошлась или хеш прошивки не совпал с
зарегистрированным) приводит к **немедленному отзыву** устройства — это защита
от подмены прошивки.

> При разработке это мешает: перезалив изменённую прошивку, вы меняете её
> SHA-256, а на шлюзе записан старый. Устройство будет отозвано при первой же
> проверке. Решение — удалить запись устройства перед перезаливкой:
> ```bash
> psql "$LACERT_PG_DSN" -c "DELETE FROM devices WHERE device_id='xiao-s3';"
> ```

## Рукопожатие

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_PENDING_HANDSHAKE_TIMEOUT` | `20s` | через сколько протухает незавершённое рукопожатие |

## Отладка и демонстрация

Эти переменные **не должны быть включены в бою**.

| Переменная | По умолчанию | Назначение |
|-----------|--------------|-----------|
| `LACERT_EMULATE_DEVICES` | `0` | сколько программных устройств поднять внутри шлюза |
| `LACERT_EMULATE_INTERVAL` | `2s` | как часто эмулированные устройства шлют телеметрию |
| `LACERT_LOG_SESSION_KEYS` | `false` | показывать сессионные ключи в журнале ротаций открытым текстом |

> **Эмуляция стирает свои данные при каждом перезапуске шлюза.** Эмулированные
> устройства генерируют новые ключи при старте, поэтому шлюз удаляет прежние
> записи `emulated-esp32-N` вместе с их телеметрией и ротациями. Выглядит как
> «пропали данные». **Записи реальных плат не затрагиваются.**

## Утилиты и тесты

Относятся не к шлюзу, а к вспомогательным программам из `cmd/`.

| Переменная | Кто использует | Назначение |
|-----------|----------------|-----------|
| `LACERT_GATEWAY_HTTP` | `devicesim`, `stresstest` | адрес REST шлюза (по умолчанию `http://localhost:8080`) |
| `LACERT_GATEWAY_TCP` | `devicesim`, `stresstest` | адрес TCP шлюза (по умолчанию `localhost:7700`) |
| `LACERT_DEVICE_ID` | `devicesim` | идентификатор симулируемого устройства |
| `LACERT_PROFILE` | `devicesim` | профиль датчиков: `climate`, `power`, `pressure`, `fuel`, `motor`. Если не задан — выбирается детерминированно по `LACERT_DEVICE_ID` |
| `LACERT_STRESS_WAIT` | `stresstest` | пауза перед началом сценариев атак |
| `LACERT_STRESS_D4_DELAY` | `stresstest` | задержка ответа в сценарии D4 (проверка, что устаревший challenge отклоняется) |
| `LACERT_TEST_PG_DSN` | тесты `pgstore` | подключение к тестовой БД; без неё тесты PostgreSQL пропускаются |

Профили задают, какие поля телеметрии шлёт симулированное устройство:

| Профиль | Поля |
|---------|------|
| `climate` | `temperature`, `humidity` |
| `power` | `voltage`, `current_a`, `power_w` |
| `pressure` | `pressure`, `temperature` |
| `fuel` | уровень топлива и сопутствующие показания |
| `motor` | `rpm`, `vibration_mm_s`, `temperature` |

Шлюз разбирает телеметрию как произвольные пары `ключ=значение`, поэтому любые
поля автоматически попадают в базу и на графики — в том числе замеры, которые
шлёт реальная плата (`heap_free`, `handshake_us` и т.д.).

## Готовые конфигурации

### Боевая

```bash
LACERT_TCP_ADDR=:7700
LACERT_HTTP_ADDR=:8080
LACERT_MQTT_ADDR=:1883
LACERT_PG_DSN=host=localhost user=lacert password=СЕКРЕТ dbname=lacert port=5432 sslmode=disable
LACERT_ADMIN_TOKEN=ДЛИННЫЙ_СЛУЧАЙНЫЙ_ТОКЕН
LACERT_CORS_ORIGINS=https://lacert.example.com
# эмуляция и вывод ключей выключены (не заданы)
```

### Демонстрационная (быстрые ротации, всё видно на глаз)

```bash
LACERT_PG_DSN=...
LACERT_ADMIN_TOKEN=...
LACERT_ROTATION_INTERVAL=20s
LACERT_ROTATION_CHECK_PERIOD=2s
LACERT_FIRMWARE_INTERVAL=20s
LACERT_EMULATE_DEVICES=0          # только реальные платы
LACERT_LOG_SESSION_KEYS=false
```

Проверить, какие переменные видит **работающий** процесс:

```bash
sudo cat /proc/$(pgrep -x gatewayd)/environ | tr '\0' '\n' | grep LACERT
```
